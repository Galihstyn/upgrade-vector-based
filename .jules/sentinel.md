## 2024-05-26 - Prevent Open Redirect via document.referrer
**Vulnerability:** The application used `document.referrer` to handle back navigation and parsed it into a URL object to check if its `origin` matched `window.location.origin`. However, it directly assigned the full `referrerUrl.href` to `window.location.href`. This is dangerous because `document.referrer` can be manipulated in some cases, and even with the origin check, if the parsed URL resolves with an origin of `"null"` (e.g. from a `javascript:` URI), it could bypass certain checks. Furthermore, an attacker could potentially inject a protocol-relative URL if the path isn't validated to start with exactly one `/` and not `//`.
**Learning:** Checking `referrerUrl.origin === window.location.origin` is necessary but not sufficient for secure internal redirects. The origin can evaluate to `"null"` in some edge cases like data or javascript URIs which might accidentally match a loose comparison if not careful, and assigning the full `href` retains the protocol and hostname which can lead to unexpected behaviors if manipulated.
**Prevention:** 1. Explicitly check `referrerUrl.origin !== "null"`. 2. Ensure the path is strictly relative by validating it starts with `/` and NOT `//` (to prevent protocol-relative redirects like `//evil.com`). 3. When redirecting internally, construct the new URL using ONLY the path components (`referrerUrl.pathname + referrerUrl.search + referrerUrl.hash`) instead of `referrerUrl.href` to guarantee the browser treats it as a relative path under the current origin.
